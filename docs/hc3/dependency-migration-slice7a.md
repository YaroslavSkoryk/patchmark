# HC-3 Slice 7A dependency-family migration record

Slice 7A closes the two dependency families reserved by the Slice 6 release
audit. It changes dependency, editor-adapter, build-adapter, test and evidence
bytes only. It does not change collaboration protocols, authority, storage,
project formats, frozen protocol fixtures, the QR disposition, or the disabled
production gate.

## Sequencing and rollback boundaries

The migrations were deliberately separated:

1. Family A moved MDXEditor, Lexical and js-yaml together. Its package tree,
   frozen hostile corpus, Node security bounds, real editor browser behavior,
   serialization/source authority, comments, patches, bookmarks, document
   switching, build and CSP/Trusted Types checks passed before family B began.
2. Family B then moved Next, PostCSS and the required lint peer. It was
   qualified through the same explicit Webpack topology used by production
   and the optimized real-authority harness.

If rollback becomes necessary before these bytes are committed, restore the
whole family, its adapter changes, and its lockfile bytes as one unit. Do not
pin a patched transitive under an unqualified major parent, combine MDXEditor
4 with Lexical 0.35 commands, or run a Next 16 default Turbopack build while
claiming Webpack-derived CSP/Trusted Types evidence. After commit, rollback
must use an ordinary reviewed revert and must preserve accepted project and
collaboration authority bytes.

## Next-generated agent guidance governance

Next `16.3.3` generated the repository-root `AGENTS.md` and `CLAUDE.md` during
`next dev` after detecting the Codex environment. Retaining both files is an
explicit repository-governance decision associated with the Next 16 migration,
not an accidental build artifact. `AGENTS.md` tells coding agents to consult
the installed, version-matched documentation under `node_modules/next/dist/docs/`
before changing Next-specific code. `CLAUDE.md` imports the same guidance for
Claude Code and is intentionally retained for cross-agent parity.

The files affect future coding-agent behavior but contain no Patchmark runtime
code, secret, application authority, permission to commit, production-
enablement authority, or permission to override higher-priority system,
developer, or user instructions. The generated Git-cleanliness sentence is
informational and never overrides task-specific working-copy instructions.
They are reviewed repository source only: the review manifest binds their
exact bytes, while production-lock source and deployable-graph scans reject
their managed marker and import text from application output.

Future Next upgrades may regenerate the managed block. Any byte change must be
inspected before commit and invalidates the relevant review evidence. Project-
specific rules must remain outside the framework-managed markers so an upgrade
cannot silently replace repository-owned policy.

## API and build adaptations

- MDXEditor 4 uses a translation override for the editable-area label. The
  override preserves every default translation and interpolation.
- A narrow render boundary maps synchronous malformed-frontmatter failures to
  Patchmark's existing Markdown-safe fallback without changing the source.
- The regression harness accepts frozen corpus cases only on its test route;
  no test selector or corpus parser is reachable from production.
- Next 16 development and production explicitly select Webpack because the
  qualified strict policy and optimized harness depend on that output/runtime.
- The optimized harness awaits Next 16's SWC binding loader before invoking
  the bundled SWC loader.
- ESLint uses Next 16's native flat presets. Compiler-only hooks diagnostics
  that were not in the pre-migration contract are documented compatibility
  exclusions, not silent warnings or audit suppression.

## Security and compatibility proof

The test-only corpus is frozen at SHA-256
`4a9afec6f85d57bfe433a9166511ed8a96683c5b0c95252855c6832a8e278e2c`.
Independent expected behavior is literal in the fixture/test and is not
regenerated by production Patchmark code. The Node verifier applies strict
UTF-8, input/output/depth/work/time budgets and verifies that hostile tags,
aliases, merges, ordered maps and prototype-shaped keys cannot execute code or
mutate prototypes. The Chrome test drives the real MDXEditor for all 15 cases.

The final package graph is documented in
`dependency-disposition-slice6.md`. Full and production-only audits are clean.
Existing collaboration fixtures remain byte-identical, QR stays pinned, and
no dependency override, resolution, vendored fork, forced audit repair, audit
suppression, new transport, telemetry or production capability was added.

The normal-production Trusted Types qualification requires every candidate
chunk URL to have the exact current page origin, including scheme and effective
port. HTTPS is required except when that same current origin uses HTTP with the
canonical loopback hostname `localhost`, `127.0.0.1`, or `[::1]`. A deployed
non-loopback page therefore cannot authorize a localhost or other loopback
script URL. `candidate.origin === window.location.origin` is mandatory;
different schemes, non-default ports, hosts, subdomains, suffix-confusion
hosts, and loopback spellings reject unless URL canonicalization makes them the
exact current origin. Credentials, query strings, fragments, `blob:`, `data:`,
`javascript:`, and paths outside the qualified `/_next/static/chunks/*.js`
shape reject. URL parsing and path normalization happen before the path test.

Normal production qualification does not use `strict-dynamic`; CSP and Trusted
Types are cumulative defenses. The optimized test-only harness does use
`strict-dynamic`, but its separate `patchmark#optimized-bundler` policy also
requires the exact current origin and exact content-hashed harness asset path.
That policy and its harness remain absent from deployable production graphs.

The tested normal policy is installed by the production-mode qualification
proxy around `next start`. It exercises the real production build and Webpack
runtime and proves that the production-optimized application is compatible
with the strict constraints. It is not yet the final deployed CSP/Trusted
Types header/bootstrap integration. Before production collaboration
enablement, the selected deployment architecture must install and requalify
the same constraints at the actual serving boundary. That is a future
enablement prerequisite, not a current localhost vulnerability; the production
collaboration gate remains disabled independently.

## Document-switching performance closure

The matched comparison uses the untouched Slice 7A starting commit
`1f4b3049717b4e9faf55a1a2c9541a9e284df58a` in an isolated worktree with its
own lockfile and dependency installation. Baseline and current use Node
`22.22.2`, npm `10.9.7`, Chrome `151.0.7922.174`, arm64 macOS `26.2`, explicit
Webpack development servers on separate ports, no CPU throttling, fresh
profiles, four warm-up switches, and three independent runs. Each run records
20 warm and 20 post-stress switches in each direction. Timing starts at the
document-selection action and ends only after the exact target identity and
semantic fingerprint are interactive and two paint frames have completed.
No samples were excluded.

The realistic project is `prj_switch_b6f72d7c3369`. Its first document is a
148,834-byte code-and-table-heavy document; its second is a 135,535-byte
table-heavy document; and its third is a 3,040-byte rapid-switch target. Exact
source hashes, structure, identity, mode transitions, raw evidence digests,
and complete distributions are frozen in
`document-switch-performance-slice7a.json`. First-to-second warm switches are
Visual-to-Visual. After the stress setup, first-to-second targets Markdown,
while second-to-first creates a fresh code-and-table-heavy Visual editor. The
previous approximately 786 ms median was the latter, not an equivalent pair of
directions. Equal controls use two structurally identical 150,498-byte
code-and-table-heavy documents.

Phase instrumentation located the regression after source/state binding and
inside MDXEditor initialization. MDXEditor 4 exposes its ref while its initial
DOM import is still running. The existing readiness effect observed the empty
intermediate DOM and called `setMarkdown` with the same target Markdown. That
doubled deferred code decorators from 220 to 440, IntersectionObserver
constructions from 272 to 544, and event-listener additions from approximately
19,127 to 39,001. Comment projection also ran against the incomplete import,
producing seven rail and three projection passes instead of the baseline five
and two. Median source/state phases remained approximately 15/16 ms, rejecting
storage reads and identity resolution as the bottleneck; the code-heavy
semantic-ready phase instead grew from 226.7 ms to 593.9 ms and paint from
409.0 ms to 819.8 ms.

The narrow fix preserves document-keyed editor ownership and exact Markdown
authority. The readiness gate now awaits an in-progress initial import of the
same target rather than applying that Markdown a second time. Deferred heavy
editors share one observer and do not auto-activate while the target editor is
transaction-busy; explicit user activation remains immediate. Comment rail
projection waits for the same transaction lock and then runs against the
accepted target DOM. Near-viewport heavy-editor presentation activation waits
for the existing 120 ms secondary-settle window after a switch, while ordinary
interactive Visual mounts and explicit activation remain immediate. The
optimized code-heavy remount has 220 decorators, one shared intersection
observer, approximately 19,688 listener additions, five rail passes, two
projections, and zero redundant `setMarkdown` calls. Its semantic-ready and
paint medians are 393.1 and 522.4 ms; the affected paint median is 36.3% lower
than the unoptimized 819.8 ms.

Across 60 samples per direction, baseline warm medians/p95 are 280.1/385.6 ms
and 332.9/412.0 ms; optimized medians/p95 are 277.8/365.9 ms and 331.6/417.2
ms. Baseline stress medians/p95 are 103.2/187.8 ms and 409.0/519.4 ms;
optimized values are 106.3/169.5 ms and 522.4/640.6 ms. Cold medians are
295.5 ms baseline and 311.6 ms optimized. Both warm directions and cold
readiness satisfy their numeric comparison limits. Equal controls remove the
asymmetry and show baseline 358.4/438.0 and 338.9/442.2 ms versus optimized
319.9/415.6 and 330.5/421.5 ms. However, the extreme development stress
direction still has a statistically credible 113.4 ms median and 121.2 ms p95
gap against its matched pre-migration direction. That residual is the fresh
MDXEditor 4 code-heavy Visual construction, not fixture direction or retained
state, and means the broader no-material-regression acceptance rule remains
open even though the reproduced unoptimized median fell by 36.3%.

All measured switches preserved exact identity/fingerprint readiness, atomic
chrome/content transitions, save state, comments, bookmark, patches, review
state and A-to-B-to-C stale-generation rejection. There were no timeouts,
runtime errors, mixed states, premature readiness events, stale commits,
cross-document writes or editor-root growth failures. Post-collection stress
heap deltas across the three optimized runs were -74,228, 4,317,020 and
-5,186,456 bytes, with no accumulating editor roots. Development-mode
MDXEditor 4 construction remains somewhat more variable than the baseline,
and does not represent retained state or weakened readiness. A further fix
must close the matched stress gap without caching mutable editor state,
weakening document-keyed ownership, or moving required semantic work outside
the primary boundary; Slice 7A is not fully commit-ready until that evidence
passes.

### Remaining code-heavy construction pass

The second pass preserved the exact first-pass initial-import await and all
document-keyed readiness boundaries. Matched development and production runs
showed that the residual is development-only: the fresh code-and-table-heavy
Visual direction measured 464.4 ms median and 568.9 ms p95 in development,
but 294.9/322.3 ms in production. The fixed development limits remain 449.9
ms median and 619.4 ms p95. The p95 passes; the median misses by 14.5 ms.
Those limits were not revised and no valid sample was excluded, so Slice 7A
remains not ready despite the additional improvement from 522.4/640.6 ms.

Complexity scaling and ablation ruled out untouched code widgets as the
remaining linear cost. With table/comment/review inputs removed, current
development medians for 0, 1, 10, 30, 60, and 110 code blocks were 106.3,
97.8, 97.7, 89.5, 98.8, and 101.2 ms. Controlled tables added about 110.8 ms;
the current code/table interaction was about 21.5 ms. Disabling code-editor
integration saved about 40 ms in a diagnostic Visual-target run, disabling
table integration saved about 66 ms, while toolbar/dialog and secondary-
activation ablations showed no benefit. Patches and versions were neutral;
comments and rail work added about 55 ms to the controlled fixture. Final
instrumentation measured plugin registration at approximately zero, code-run
node creation at 0.1 ms, inert code DOM at 0.5 ms, native table DOM at 4.4 ms,
and the encompassing development MDXEditor/Lexical construction/import phase
at 491.5 ms.

The retained safe change compacts only runs of at least eight adjacent simple
fenced code blocks into one internal Lexical node. The node owns literal code,
language, and metadata, exports the original MDAST code nodes, and expands
atomically to real MDXEditor code nodes when a block nears the viewport or is
explicitly clicked, focused, or keyboard-activated. A four-entry process-local
LRU makes preparation idempotent under repeated development rendering; the
internal descriptor is neither a protocol object nor accepted production
input. Literal user-authored internal-language fences remain ordinary code.
Short and unusual runs follow the normal parser. Inert code and table roots
also use layout/paint containment. Browser qualification proves search through
Chrome find, copy, selection, language/metadata preservation, activation,
edit, export, and reopen.

The initial heavy-widget count is zero and the maximum around the viewport is
eight. A deliberate full traversal can activate all 110 widgets; because
CodeMirror has no safe deactivation contract, those activated editors remain
bounded by the current document until switch. Returning to the top therefore
retains 110, while switching documents releases all of them immediately.
Post-switch ownership accounting reports one Lexical listener, zero CodeMirror
listeners, zero MDXEditor toolbar/dialog listeners, and zero CodeMirror roots.
Collected stress heap deltas were 382,832, 361,444, and 453,684 bytes without
root accumulation.

Rejected candidates remain out of the source: a semantic adjacent-table run
regressed the corrected probe to 508.8 ms; `content-visibility` broke automatic
scroll-into-view activation; inline-size, run-wrapper, and whole-editor
containment either regressed or provided no reliable benefit. The accepted
layout/paint containment retained the exact viewport and explicit-activation
tests. Primary distributions ran without listener/observer interception;
detailed ownership accounting was a separate diagnostic. A matched 10-switch
fresh-profile diagnostic measured 272.6/384.9 ms first-usable/secondary-settle
medians without interception and 263.8/378.0 ms with it. Direction-specific
first-usable differences were -5.0 ms and +6.7 ms, so interception overhead was
below run-to-run noise and was not used to adjust any primary result.

Across the final three fresh profiles and 60 samples per direction,
development warm medians/p95 were 311.3/406.5 and 292.2/390.0 ms; stress was
121.4/169.4 and 464.4/568.9 ms. Equal controls were 275.9/384.2 and
300.6/401.7 ms. Production warm was 223.6/254.5 and 198.9/239.5 ms; stress was
103.6/111.0 and 294.9/322.3 ms. Production equal controls were 222.9/239.8
and 252.2/262.2 ms. There were zero failures, timeouts, runtime errors, mixed
states, premature readiness events, stale commits, cross-document writes,
redundant `setMarkdown` calls, or editor-root growth failures.

This pass does not change dependencies, the lockfile, protocols, persistence,
CSP, Trusted Types, collaboration capability, production enablement, frozen
fixtures, `AGENTS.md`, or `CLAUDE.md`. Production collaboration remains locked
and the overall release classification remains `conditional` for Slice 7B.
The exact second-pass distributions, raw hashes, scaling, phase, ablation,
resource, correctness, and rejected-candidate evidence are frozen in
`document-switch-performance-slice7a.json`.

### Surgical final pass

The final bounded pass first established the missing untouched-commit
production baseline with the baseline lockfile, Webpack build, `next start`,
Node 22.22.2, npm 10.9.7, and Chrome 151.0.7922.174. Its realistic production
stress medians/p95 were 114.2/136.2 and 246.1/317.8 ms. The matched equal
controls were 118.9/136.8 and 237.1/291.5 ms. All runs used fresh profiles,
four warmups, 20 measured samples per direction, and retained every valid
sample.

Focused comment controls isolated a 21.0 ms fixed first-anchor cost and about
0.67 ms per additional selected-text comment. The 31-comment target performed
two complete projections, five rail passes, and 93 card measurements; the
second mutation-triggered pass rebuilt the same accepted Visual DOM text index.
The retained scheduler now coalesces accepted document-switch work over two
generation-bound animation frames, cancels superseded work, and reuses the
already resolved canonical anchor inside one projection. Ordinary mode and
comment interactions retain the original one-frame response. Floating-card
height state no longer retriggers measurement solely because its derived layout
object changed. The matched diagnostic fell from 282.5 to 250.4 ms, projection
passes from two to one, rail passes from five to four, card measurements from
93 to 62, and projection CPU from 41.2 to 24.0 ms. No cross-document geometry
cache was introduced; DOM mutation, resize, identity, generation, Markdown,
comment, patch, mode, bookmark, re-anchor, and cleanup boundaries continue to
invalidate scheduled work.

The table controls measured 106.1 ms for no tables, 107.6 ms for one nine-row
table, 242.9 ms for 26 nine-row tables, and 157.8 ms for byte-matched
paragraphs. The resulting semantic-table delta was about 85.1 ms: 36.3 ms of
GFM parse/import above the byte-matched control, 2.5 ms of native table DOM,
and the remainder in Lexical table integration, controls/listeners, observation,
and layout. Existing native deferral already omits offscreen nested cell editors
and affordances. No further change was accepted because table compaction,
generic virtualization, `content-visibility`, and broader containment cross
previously rejected correctness or performance boundaries.

The corrected final primary batch ran without listener/observer interception.
One earlier intercepted development batch is retained separately as a declared
configuration error and was not used for acceptance. Final development warm
medians/p95 were 242.1/332.0 and 268.8/354.7 ms; stress was 123.5/169.4 and
457.4/569.8 ms. Production warm was 186.6/196.2 and 202.3/216.9 ms; stress was
107.7/136.3 and 266.2/296.1 ms. All atomicity and lifecycle counters remained
zero. The production result improved materially, and the development p95 passes,
but the development median still exceeds the immutable 449.9 ms limit by
7.5 ms. Therefore the performance regression is not resolved and Slice 7A
remains blocked and not ready to commit. The full historical comparison,
production baseline, diagnostics, distributions, raw hashes, and failed
decision are frozen in `document-switch-performance-slice7a.json`.
